# GPS_DATA 数据协议规范

| 项 | 值 |
|---|---|
| 版本 | v1.1（已实现；待确认项见 §8 的实现登记） |
| 适用固件 | GD32F4xx Template（`main.c` / `info_bsp.c`） |
| 数据源 | 司南导航 K922 GNSS 模组（`$GPYBM` / `$GPNAV` ASCII 语句） |
| 输出去向 | 调试串口（USART0, 115200-8-N-1） |
| 参考文档 | K922 OEM 板卡参考手册 3.3.1.4.4（GPYBM）、3.3.1.4.5（GPNAV）<br>本机路径：`tmp/k922/proto.txt` |

---

## 1. 范围

本协议规定：

1. 接收端如何识别 K922 的 `$GPYBM` / `$GPNAV` 语句；
2. 如何把这两种语句转换成统一的数据结构 `GPS_Module_Info`；
3. 转换后通过串口输出的文本格式；
4. 无效数据、异常帧、状态位的处理规则；
5. 验收用的测试用例与交叉校验公式。

语言/编码：**ASCII 文本**，全部字段为可打印字符，无二进制字段。

---

## 2. 系统链路

```
 K922 模组 ──UART(115200-8-N-1, 模块 COMx)──► MCU USART5 (PC6/PC7, AF8)
                                                   │  IDLE+DMA 收帧
                                                   ▼
                                         info_bsp.c 解析 → GPS_Module_Info
                                                   │
                                                   ▼
                                     MCU USART0 (PA9/PA10) ──► 上位机/调试口
```

## 3. 输入协议（K922 侧）

### 3.1 语句格式

```
$<语句名>,<字段2>,<字段3>,...,<字段N-1>*<校验和><CR><LF>
```

| 项 | 规定 |
|---|---|
| 起始符 | `$` |
| 字段分隔 | `,`（ASCII 0x2C） |
| 校验和 | `*` 后接 2 位十六进制大写字符；值为 `$` 之后、`*` 之前所有字符的逐字节 XOR |
| 结束符 | `<CR><LF>`（0x0D 0x0A） |
| 字段号 | 从 1 开始计数，**字段 1 是语句名本身**（含 `$`） |
| 空字段 | 两个连续逗号表示该字段无效（不是 0） |
| 有效位数 | 见各语句字段表；解析时不得按"固定字符数"截取 |

### 3.2 本协议使用的两种语句

| 语句 | 手册章节 | 输出周期（建议） | 提供的关键量 |
|---|---|---|---|
| `$GPYBM` | 3.3.1.4.4 | 1 Hz | 位置、椭球高、航向、俯仰、速度、投影坐标、**基线长**、主站收星数 |
| `$GPNAV` | 3.3.1.4.5 | 1 Hz | 位置、**海拔高**、高程异常、航向、俯仰、速度、**定位状态**、**航向解状态**、系统掩码、基线长 |

## 4. 数据模型

```c
typedef struct GPS_Module_Info {
    double  latitude;           /* 纬度, 度, 北正南负, 输出 6 位小数 */
    double  longitude;          /* 经度, 度, 东正西负, 输出 6 位小数 */
    double  ElpHeight;          /* 高度, m（见 5.3 基准备注）, 输出 6 位小数 */
    double  Heading_Angle;      /* 航向角, 0–360°, 真北基准, 输出 6 位小数 */
    double  Baseline;           /* 双天线基线长, m, 输出 6 位小数 */
    double  default_base_line;  /* 标称基线长（配置常量）—— 见 9.1 待确认 */
    uint8_t GPS_Satellite;      /* 卫星数, 整数（口径见 5.3） */
} GPS_Module_Info;
```

## 5. 转换规则

### 5.1 字段映射表

| 结构体成员 | `$GPYBM` 来源 | `$GPNAV` 来源 |
|---|---|---|
| `latitude` | ID 4 Lat | ID 7 Latitude |
| `longitude` | ID 5 Lon | ID 8 longitude |
| `ElpHeight` | ID 6 ElpHeight（**椭球高**） | ID 9 Altitude（**海拔高**，见 5.3） |
| `Heading_Angle` | ID 7 Heading | ID 12 Heading |
| `Baseline` | ID 22 Baseline length | ID 22 Baseline length |
| `GPS_Satellite` | ID 19 SVn（主站收星数） | ID 23–27 #SV Used **各非空值求和** |
| `default_base_line` | 不来自语句（配置常量） | 同左 |
| 定位状态（建议输出） | ID 17 Position status | ID 19 Status1 |
| 定向状态（建议输出） | ID 18 Heading status | ID 20 Status2（`N*`=无效） |

> `default_base_line`、两项状态不在现有 6 行输出里；状态作为 v1.1 扩展项（见 7.4）。

### 5.2 解析要求（必须遵守）

1. **按逗号切分取字段**，不得使用"跳过非数字字段、只收集数字"的方式。
   反例：以"数字+逗号"为循环条件时,`SN00016361`（ID 2）与 `VN`（ID 20）这类**文本字段会被整段跳过**,
   导致其后所有字段索引平移 —— GPYBM 平移 2、GPNAV 平移 1,且 GPNAV 在 ID 20 之后再平移 1 位。
2. 空字段必须与"数值 0"区分：空 → 该成员**无效**（见 8.3）。
3. 解析必须在**已知长度**的缓冲区内进行（`memchr`/显式长度），不得依赖 `'\0'` 结尾。
4. 校验和错误 → 整句丢弃（见 8.1）。
5. 字段数量不足（未达表中最后必需字段）→ 整句丢弃。

### 5.3 单位与基准（**易错点**）

| 量 | 规定 | 说明 |
|---|---|---|
| `ElpHeight` | **单位 m**。GPYBM 给的是**椭球高**；GPNAV 给的是**海拔高** | 两者相差一个高程异常值 N：<br>**椭球高 = 海拔高 + N**；<br>N 见 GPNAV ID 10 Separation（本机实测 ≈ `-16.2776`） |
| 交叉校验 | `GPYBM.ID6 ≈ GPNAV.ID9 + GPNAV.ID10` | 实测 `55.516 ≈ 71.7937 + (-16.2776) = 55.5161` ✓ |
| `Heading_Angle` | 真北基准、顺时针、0–360°；**未加磁偏角改正** | 若要磁北参考需设备端 `MAGVAR` 或上位机换算 |
| `Baseline` | 主/从天线相位中心距离，m | 与 `default_base_line` 比较可判定基线异常 |
| `GPS_Satellite` | GPYBM：主站天线收星数；GPNAV：各系统参与解算星数之和 | **两种来源口径不同**，混用会造成跳变 |

### 5.4 同一秒收到两句时的取舍

上位机（K922）在本固件配置下每秒输出 `$GPYBM` 与 `$GPNAV` 各一句，硬件缓存区中两句相邻。
必须显式定义取舍规则，否则输出随帧内顺序变化。**建议规则（待确认，见 9.2）：**

- **按句输出**：每识别到一句有效语句就输出一组，并用 v1.1 的 `source` 行标明来源（推荐，信息不丢）；
- 或**按秒输出一次**：同一秒内后到的有效语句覆盖先到的（`last-wins`）；
- 或**按秒输出一次**：GPYBM 优先（因为它直接提供椭球高、基线长、主站收星数）。

## 6. 输出协议

### 6.1 文法

```
<block>      ::= <line> <line> <line> <line> <line> <line>
<line>       ::= "[GPS_DATA]:" <name> ":" <value> <EOL>
<name>       ::= "latitude" | "longitude" | "ElpHeight"
               | "Heading_Angle" | "Baseline" | "GPS_Satellite"
<value>      ::= <fixed6> | <uint>
<fixed6>     ::= [-] <digits> "." <6 digits>          ; 相当于 printf("%f")
<uint>       ::= <digits>                             ; GPS_Satellite 用 printf("%d")
<EOL>        ::= "\r\n"                               ; 见 6.3
```

### 6.2 字段顺序与格式（**固定，不得变动**）

| 序号 | 输出行前缀 | 值来源 | 格式 | 单位 |
|---|---|---|---|---|
| 1 | `[GPS_DATA]:latitude:` | `latitude` | `%f`（6 位小数） | 度 |
| 2 | `[GPS_DATA]:longitude:` | `longitude` | `%f` | 度 |
| 3 | `[GPS_DATA]:ElpHeight:` | `ElpHeight` | `%f` | m |
| 4 | `[GPS_DATA]:Heading_Angle:` | `Heading_Angle` | `%f` | 度 |
| 5 | `[GPS_DATA]:Baseline:` | `Baseline` | `%f` | m |
| 6 | `[GPS_DATA]:GPS_Satellite:` | `GPS_Satellite` | `%d` | 颗 |

### 6.3 行结束符

**实际值：`\r\n`（0x0D 0x0A）** —— 自 v1.1（2026-10-14）起生效，已登记于 §9 变更记录。
v1.0 固件使用 `\n`；按行解析的上位机（先按 `\n` 切分、再去掉行尾 `\r`）对两种写法都兼容。

### 6.4 输出速率与时机

- 触发：每识别到一句**有效**语句输出一组（或按 5.4 所选规则）；
- 速率：不超过输入速率（K922 `LOG … ONTIME 1` → ≤1 Hz/句）；
- 顺序：同一组的 6 行必须**连续、不可插队**（不允许被其它调试打印打断）；
- 阻塞：输出为阻塞发送，单组约 130 字节 → 115200 下约 11 ms，需在时间预算内。

### 6.5 输出示例（单组）

```
[GPS_DATA]:latitude:27.852472
[GPS_DATA]:longitude:112.965327
[GPS_DATA]:ElpHeight:55.516000
[GPS_DATA]:Heading_Angle:122.537000
[GPS_DATA]:Baseline:0.951000
[GPS_DATA]:GPS_Satellite:22
```

### 6.6 v1.1 扩展行（**规格保留，当前未输出**）

> 实现状态（2026-10-14 现场要求）：控制台**只输出 §6.2 的 6 行**，本表的追加行不输出。
> 解析层已经具备这些量（`gps_fix_t` 的 `source` / `position_status` / `heading_status` / `valid` / `utc`），
> 其中 `source` 与 `valid` 已用于下行链路帧的 `flag` 位（bit1 / bit0）。
> 需要启用时，只需在 `main.c: gps_report_print()` 末尾按本表追加 5 行即可，无需改解析器。
> 建议取值：`position_status` / `heading_status` 无值输出 `255`（`GPS_STATUS_NONE`）；
> `utc` 无值输出 `-`；GPNAV 的 `heading_status` 直接输出 `NN/NV/VN/VV` 文本。

| 追加行 | 含义 | 取值 |
|---|---|---|
| `[GPS_DATA]:source:` | 本组数据来源句 | `GPYBM` / `GPNAV` |
| `[GPS_DATA]:position_status:` | 定位解状态 | 0/1/2/3/4/5（定义见 3.3/3.4） |
| `[GPS_DATA]:heading_status:` | 定向解状态 | GPYBM：0/1/4/5；GPNAV：`NN/NV/VN/VV` |
| `[GPS_DATA]:utc:` | 本组 UTC 时间 | `hhmmss.ss` |
| `[GPS_DATA]:valid:` | 本组是否可用 | `1`=位置与航向均有效, `0`=含无效项 |

> 引入 `position_status` / `heading_status` 的动机：现有 6 行中"真实的 0"与"无效值 0"无法区分
> （实测单点定位/定向未定位时航向与基线本就为 0）。

## 7. 有效性与异常处理

### 7.1 帧级

| 条件 | 处理 |
|---|---|
| 未收到 `$` 开头 / 无 `*` | 丢弃该行 |
| 校验和与 `*` 后两位不符 | 丢弃该行 |
| 字段数少于所需（GPYBM < 23、GPNAV < 22） | 丢弃该句 |
| 单帧长度超过接收缓冲 | 丢弃并计数（`drop`） |
| 接收中断溢出（ORERR） | 清标志 + 计数（`err`），不影响后续帧 |
| 超时：> 3 × 标称周期（本配置 3 s）未收到任一句 | 上位机应判定"数据超时"，见 7.3 |

### 7.2 字段级

| 条件 | 处理 |
|---|---|
| 该字段为空 | 该成员标记无效；**不得输出为有效 0** |
| 字段非数字（含 `SN…`、`VN` 等） | 该字段无效；解析器不得因此错位（见 5.2） |
| 数值超出物理范围（纬度 ±90、经度 ±180、航向 0–360） | 该成员无效 |
| 高度跳变 > 阈值（建议 10 m/s） | 可标记可疑（可选） |

### 7.3 无效值的输出约定（必须二选一并写明）

> **当前采用方案 B（v1.0 兼容）**：固件只输出 §6.2 的 6 行数值，不带状态行；
> 因此"真实的 0"与"无效值 0"在串口上仍不可区分（现场要求简洁输出）。
> 需要区分时按 §6.6 追加状态行，或读下行链路帧的 `flag.bit0`（= `valid`）。
>
> **方案 A（推荐，v1.1）**：照常输出 6 行数值（无效项输出 `0.000000`），
>
> **方案 A（推荐，v1.1）**：照常输出 6 行数值（无效项输出 `0.000000`），
由 `position_status` / `heading_status` / `valid` 行表达有效性。上位机必须先读状态行再使用数值。

**方案 B（v1.0 兼容，不推荐）**：无效项直接输出 `0.000000` 且无状态行 ——
上位机无法区分"真实 0"与"无效"，仅在调试阶段可接受。

### 7.4 已知现场判读要点

| 现象 | 含义 |
|---|---|
| `position_status = 1` 持续 | 单点解，无差分/未 RTK，位置为米级 |
| `heading_status = 0` 或 `Status2` 含 `N` | 定向无效 → 航向/俯仰/基线无意义（输出 0 属正常） |
| `Baseline` 远小于实物基线 | 从天线馈线/接头/增益异常，或定向未固定 |
| 星数与 `Baseline` 同秒跳变 | 两句来源口径不同（见 5.3），按 5.4 统一口径 |

> - 9.6 **未输出**（`utc` / 状态行规格保留，见 §6.6；数据已在解析层与下行链路中可用）；
> - 9.1 仍不输出 `default_base_line`（配置常量）。
>
> 解析实现于 `info_bsp.c: gps_fix_parse_one()` / `gps_fix_next()`；旧接口 `gps_info_rsl()` 保留为兼容包装；
> 解析缓冲为文件级 static（不占任务栈，见该文件注释）。

## 附录 A：测试用例（用真实样本验收）

> 样本取自 2026-10-13 实测串口日志（时间 09:24:02 与 09:24:15）。

### A.1 `$GPYBM` 用例

输入：
```
$GPYBM,SN00016361,092402.00,+27.852472239,+112.965327110,55.516,122.537,85.762,0.003,-0.010,-0.042,0.010,3102058.824,-193871.697,,,1,5,22,0,,0.951,22,*4E
```
期望输出（`%f` = 6 位小数）：
```
[GPS_DATA]:latitude:27.852472
[GPS_DATA]:longitude:112.965327
[GPS_DATA]:ElpHeight:55.516000
[GPS_DATA]:Heading_Angle:122.537000
[GPS_DATA]:Baseline:0.951000
[GPS_DATA]:GPS_Satellite:22
```
逐项来源：ID4 / ID5 / ID6 / ID7 / ID22 / ID19。

### A.2 `$GPNAV` 用例

输入：
```
$GPNAV,20261013,092415.00,18,4,,27.85247447971,112.96532616184,72.4029,-16.2776,272.830,104.600,80.830,,-0.014,-0.000,0.005,0.014,1,VN,5,1.254,7,0,11,,,7,0,11,,,,,,,*64
```
期望输出：
```
[GPS_DATA]:latitude:27.852474
[GPS_DATA]:longitude:112.965326
[GPS_DATA]:ElpHeight:72.402900
[GPS_DATA]:Heading_Angle:104.600000
[GPS_DATA]:Baseline:1.254000
[GPS_DATA]:GPS_Satellite:18
```
逐项来源：ID7 / ID8 / ID9（海拔高）/ ID12 / ID22 / ID23–27 求和（`7+0+11`）。
一致性验算：`System Mask = 5`（GPS+BDS）与 `#SV Used = 7,0,11` 吻合（GPS 7 颗 + BDS 11 颗）。

### A.3 交叉校验用例（同一秒的两句必须自洽）

同一秒的 `$GPYBM` 与 `$GPNAV` 描述同一物理量，可用于验证解析是否正确。
实测（2026-10-13，09:24:02 与 09:24:15 两组）：

| 校验项 | 公式 | 09:24:02 | 09:24:15 |
|---|---|---|---|
| **椭球高 ↔ 海拔高** | `GPYBM.ID6 = GPNAV.ID9 + GPNAV.ID10` | `55.516 = 71.7937 + (-16.2776) = 55.5161`（差 0.0001 m） | `56.125 = 72.4029 + (-16.2776) = 56.1253`（差 0.0003 m） |
| 航向 | `GPYBM.ID7 = GPNAV.ID12` | `122.537 = 122.537` ✓ | `104.600 = 104.600` ✓ |
| 基线长 | `GPYBM.ID22 = GPNAV.ID22` | `0.951 = 0.951` ✓ | `1.254 = 1.254` ✓ |
| 纬度 | `GPYBM.ID4 = GPNAV.ID7` | 完全一致（差 0） | 完全一致（差 0） |

> 差值仅来自小数位舍入（GPYBM 3 位 vs GPNAV 4 位），量级 1e-4 m 属正常。
> 若这四项中任一项对不上，说明字段号取错（见 A.4）。

### A.4 反例（用于回归测试，必须**失败**）

以下错误特征在 v1.0 固件曾出现，回归测试须确保不再出现：

| 错误特征 | 原因 |
|---|---|
| 输出 `latitude` 等于输入**经度**、`longitude` 等于输入**椭球高**、`ElpHeight` 等于输入**航向**、`Heading_Angle` 等于输入**俯仰** | 字段索引整体 +1（解析被 `SN…` 文本字段顶偏） |
| `Baseline` 恒为 `0.000000`（实际 ID22 非 0） | 基线长取错字段 |
| `GPS_Satellite` 恒为 `0`（实际 ID19 = 22/23） | 星数取错字段 |
| 只有 `$GPYBM` 的数值生效，`$GPNAV` 无任何效果 | 解析循环遇首个 `*` 即停，未逐句处理 |

### A.5 边界用例：定向未定位（"真实的 0"）

输入（09:24:01，该帧 `ID17=1` 单点定位、`ID18=0` 定向未定位、`ID22=0.000`）：
```
$GPYBM,SN00016361,092401.00,+27.852470107,+112.965320508,55.385,0.000,0.000,-0.018,-0.008,0.012,0.019,3102058.624,-193872.364,,,1,0,15,0,,0.000,0,*4E
```
期望输出：
```
[GPS_DATA]:latitude:27.852470
[GPS_DATA]:longitude:112.965321
[GPS_DATA]:ElpHeight:55.385000
[GPS_DATA]:Heading_Angle:0.000000      ← 定向未定位，此处 0 是"真实的 0"
[GPS_DATA]:Baseline:0.000000            ← 同上
[GPS_DATA]:GPS_Satellite:15
```
**要点**：这组输出与"解析错位导致的 0"外观相同——这正是必须引入
`position_status` / `heading_status`（v1.1，见 6.6）才能让上位机区分二者的原因。
验收时应把此用例与 A.4 的反例一起跑：两者数值都可能是 0，**唯一区别在状态行**。
